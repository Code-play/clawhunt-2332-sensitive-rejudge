## 2. How a run works

One run is one transaction; order follows the ticket (rules first, model second).

1. **Masking gate.** Direct identifiers (mobile numbers, e-mail addresses, 16-19
   digit card numbers, 18-character ID numbers, optional name roster) become typed
   placeholders such as `[PII:PHONE]`. The model only sees masked text, and the
   masked text is the reference for quote verification.
2. **Batching.** Segments are sent 30 at a time with one segment of context on
   each side; roles (`target`, `context_before`, `context_after`) and
   `target_seqs` travel in the payload.
3. **Rule stage.** Upstream contract: `detect(segments) -> list[RuleHit]` (`seq`,
   `quote`, `flag_type`, `rule_code`, `reason`). A deterministic regex stub ships
   with the ticket, and real rule hits can be passed through the API.
4. **Model.** The answer may be plain JSON, code-fenced or wrapped in prose; every
   flag is validated on its own (allowed type, reason <= 40, confidence 0..1, no
   unknown fields) and rejected entries are counted, never silently dropped.
5. **Merge and persist.** Survivors are written to `ip_sensitive_flags` with
   `disposition = 'pending'`.

The same function (`moderation.pipeline.detect_document`) serves the API and the
offline evaluation, so the evaluated numbers describe production code.

## 3. Prompt contract (`ip.sensitive.v1`)

Input: masked segments, 30 per batch, plus one context segment on each side.
Output: one JSON object `{"flags": [{"seq", "quote", "flag_type", "reason",
"confidence"}]}`, with `flag_type` in `third_party_personal` /
`unpublished_business` / `unlicensed_brand` / `other`, `quote` copied verbatim
from the segment, `reason` at most 40 characters, `confidence` between 0 and 1.

The prompt encodes the ticket's policy: over-flag rather than miss (宁可多标、不能漏标),
recall-first evaluation, no monetary reasoning (AI 不计算金额), no disposition
decision, no external sending, and "this output is an L1 draft for staff review".
The front matter is machine-checked: changing the batch size, context, flag types,
reason limit, version prefix or one of the required instructions fails the tests
instead of silently changing behaviour.

## 4. Merge contract (implemented literally)

- A fragment hit by rule and model becomes one row with `detector = 'rule+model'`.
- A model-only hit with `confidence < 0.5` is dropped.
- A `quote` not found verbatim in the masked segment is dropped.
- Everything else is kept.

Overlap defines "same fragment": hits in one segment whose spans intersect become
one record whose span is the union, so the stored quote is always verbatim text.
The rule's `flag_type` wins when rule and model disagree; merged confidence is the
highest member. A low-confidence model hit overlapping a rule hit is kept (only
model-only hits are dropped). Repeated text is flagged once, at its first
occurrence. A model flag on a context segment is kept (recall-first) and reported
as `context_seq_flags`.

A unique expression index on (`content_id`, `segment_seq`, `md5(quote)`) where the
row is live makes a second row for the same fragment impossible, so re-running the
pipeline is idempotent (`written = 0`, `skipped_duplicates > 0`).

## 5. Data model and migration

`ip_sensitive_flags` follows the platform convention (`id` UUID, `org_id`,
`site_id`, `created_at`, `created_by`, `updated_at`, `deleted_at`) and adds
`content_id`, `run_id`, `segment_seq`, `quote`, `quote_start`, `quote_end`,
`flag_type`, `detector`, `confidence numeric(4,3)`, `reason <= 40`, `rule_code`,
`prompt_version`, `disposition` (default `pending`), `reviewed_by`, `reviewed_at`,
`review_note`.

PostgreSQL enforces the contract, not only the application: CHECK constraints for
detector, flag type, disposition, confidence range, reason and quote length, span
validity, and a review state that cannot be half-set. The migration has a real
`downgrade()`; `upgrade -> downgrade base -> upgrade` and `alembic check` are in
the suite.

## 6. HTTP API

- `POST /v1/ip-drafts/{content_id}/sensitive-review` runs a re-review and returns
  the summary (mask replacements, per-batch accepted/rejected codes, kept,
  `dropped_by_code`, written, skipped duplicates) plus the flags it wrote.
- `GET /v1/ip-drafts/{content_id}/sensitive-flags` lists the queue with
  `disposition`, `limit`, `offset`.
- `GET /v1/sensitive-flags/{flag_id}` returns one flag.
- `PATCH /v1/sensitive-flags/{flag_id}` records the staff disposition (`accepted`
  / `dismissed`, reviewer, optional note); `pending` cannot be set by staff.
- `DELETE /v1/sensitive-flags/{flag_id}` soft-deletes for audit.
- `GET /healthz` reports prompt version, batch size, model mode, confidence floor.

Tenant identity is part of every request; cross-tenant ids return a plain 404.

## 7. Evaluation

The fictional set has 8 drafts and 24 gold fragments; the recorded model answers
deliberately contain a paraphrase, a low-confidence guess, an unknown flag type
and a context-segment flag, so the drop paths are exercised rather than assumed.

**Recall 95.83 % (23/24), precision 76.67 % (23/30)** against the required recall
>= 95 % and precision >= 60 %. Matching is fragment level: a detection and a gold
fragment match when they share at least half of the shorter span in the same
segment and, for the primary metrics, carry the same flag type; span-only numbers
are reported alongside. The report lists the one missed fragment and every
over-flagged fragment, so the numbers are auditable. `ipsensitive.eval_cli` exits
non-zero when a threshold is missed and is CI-ready.

## 8. How to run

```bash
docker compose up -d db
pip install -e ".[dev]"
export DATABASE_URL=postgresql+psycopg://ipsensitive:ipsensitive_local_dev@127.0.0.1:55432/ipsensitive
alembic upgrade head
uvicorn --factory ipsensitive.api.main:create_app --port 8000
python -m ipsensitive.eval_cli
python -m pytest
python examples/http_demo.py
```

Model access is environment-only: `IP_SENSITIVE_MODEL_MODE=recorded` replays the
shipped fixture (tests, evaluation, demo); `http` posts to
`$IP_SENSITIVE_MODEL_BASE_URL/chat/completions` (OpenAI-compatible,
`response_format: json_object`) with the standard library, so no SDK can send data
out of the client's cloud account. `IP_SENSITIVE_ON_MODEL_ERROR=fail` aborts a run
and writes nothing; `rules_only` keeps rule-stage flags and marks the run degraded.

## 9. Integration points

- **Upstream rule engine.** Replace `RegexRuleDetector.detect` with the real rule
  result, or keep the stub and send `rule_hits` in the POST body (on masked text).
- **Drafts table.** `content_id` is a plain UUID; add the FK to `ip_drafts` and the
  tenant-ownership check when that ticket lands.
- **Authentication.** The service trusts `org_id`, `site_id`, `created_by` and
  `reviewed_by` from the request; the gateway must inject them from the
  authenticated staff session. No auth is implemented here by design.
- **Model gateway.** Point `IP_SENSITIVE_MODEL_BASE_URL` at the client-side
  gateway; the prompt version travels in every payload and is stored per row.
- **Review workbench.** The queue exposes masked quotes with `quote_start` /
  `quote_end` offsets for red-flag highlighting; raw offsets are deliberately not
  stored, so the queue cannot leak identifiers the masking gate removed.

## 10. Guarantees and limitations

Guaranteed by code and tests: mask-only storage; per-entry model validation; the
three merge rules; idempotent re-runs; tenant-scoped reads and 404s; no outbound
call other than the configured model gateway; no monetary computation anywhere;
migration round-trip with no model drift.

Limitations, stated honestly:

- The rule detector is a stub with the upstream contract, not the client's engine.
- The evaluation, tests and demo use recorded answers of a fictional model; the
  HTTP mode is unit-tested with a fake transport, not against a live gateway.
- 24 gold fragments is a demonstration set sized for this ticket, not a
  production calibration corpus; the harness accepts any larger set with the same
  schema.
- No UI, no queue assignment, no rework workflow: staff disposition is the API.
- Model outage behaviour is a configuration choice, not automatic failover.

## 11. Confidentiality

Every person, enterprise, brand, phone number, e-mail address and ID number in the
code, tests, evaluation set and reports is invented for this ticket. No real
personal or enterprise information is used and the client's name does not appear
in the deliverable. The only outbound call is the configured model gateway, and it
receives masked text only.
